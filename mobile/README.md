# Android-приложение «Деффектор»

Приложение по [плану Павла](../plan/pavel-mobile-ar.md): Kotlin, Jetpack Compose,
CameraX, встроенные ML Kit QR и Latin Text Recognition, Retrofit/OkHttp,
kotlinx.serialization. Android 8.0 и новее (`minSdk 26`), портретная ориентация.

**APK:** [dist/deffector-debug.apk](dist/deffector-debug.apk). Сборка для хакатона,
подписана отладочным ключом. Инструменты разработки и кеши в `.tools/` в Git не входят.
Итоговый APK включает интерфейс и трекер из `main` (`8c79915`) и исправление поздней
ошибки распознавания, которая могла подменять состояние выбранного анализа.
Сборка: 22 JUnit-теста, Android Lint без ошибок (11 предупреждений).
SHA-256 — `0252af99e1ec93c92919fa09fcd1a50e449e937951e3dfc0775cddbbbc99b09c`.

## Сборка в Windows

Нужен Python 3.10+. Если `python` отсутствует в PATH, используйте `py` — на ПК Павла
работает именно эта команда. Из корня репозитория:

```powershell
py mobile/build.py --setup
```

Первая команда скачивает Microsoft OpenJDK 17, Gradle 8.9, Android command-line tools,
SDK 35, build-tools и platform-tools в `mobile/.tools/`, принимает лицензии Android SDK,
затем скачивает зависимости приложения, запускает тесты, Android Lint и сборку.
Нужен интернет **только при подготовке среды**. Собственные скрипты проекта — на Python.

Повторная сборка после заполнения кеша:

```powershell
py mobile/build.py --offline
```

Результат — `mobile/dist/deffector-debug.apk`. Если сеть нужна для новых зависимостей,
запустите `py mobile/build.py` без `--offline`. Скрипт публикует APK в `dist/` только
после успешных тестов, Lint и сборки. Исходники можно открыть как проект в Android Studio;
при выборе локального Gradle укажите `mobile/.tools/gradle-8.9`, JDK — `.tools/jdk`.
Повторная сборка проверена в Windows из папки с кириллицей в пути.

## Установка и подключение

Включите на телефоне режим разработчика и отладку по USB, подключите кабель и
подтвердите отпечаток ключа ПК на телефоне.

```powershell
mobile/.tools/sdk/platform-tools/adb.exe devices -l
mobile/.tools/sdk/platform-tools/adb.exe install -r mobile/dist/deffector-debug.apk
```

Либо сборка и установка одной командой: `py mobile/build.py --offline --install`.
Если устройств несколько, добавьте `--serial <номер из adb devices>`.
У сборки от 14.11 новый отладочный ключ. Если ранее был установлен APK от 13.11,
удалите его перед установкой. При удалении сбросятся сохранённые адрес ПК и вход.
История осмотров хранится на ПК.

Запустите `py stand.py` из корня, соедините телефон и ПК одной локальной сетью.
На ПК Павла проверена точка доступа телефона; после смены сети адрес ПК может измениться.
В приложении откройте «Настройки», введите **адрес из окна стенда**
(`http://<локальный IPv4>:8000`). Нажмите «Сохранить», затем «Проверить связь».
Статус показывает отдельно бэкенд, состояние и режим ИИ (`stub` — заглушка).

**Вход.** После адреса приложение открывает экран входа: почта и пароль учётной записи
(демо-записи — в `backend/README.md`, «Вход, роли, отчёты»). Токен хранится в настройках
приложения и уходит в заголовке `Authorization` каждого запроса; имя и роль видны под
заголовком на экране камеры и в «Настройках», там же «Выйти». Если сервер отвечает, что
вход истёк, приложение возвращает на экран входа. Смена адреса ПК завершает вход.
Кнопки зависят от прав роли: без права `inspect` нет «Начать AR-осмотр» и регистрации
осмотра, с правом `report` на вкладке «Обзор» есть панель «Отчёт об осмотре».

**Отчёт.** «Выгрузить отчёт в PDF» или «в Excel» → системное окно выбора места сохранения →
файл формирует сервер, приложение записывает его в выбранное место; «Открыть сохранённый
отчёт» передаёт файл программе просмотра на телефоне.

**Вход, роли и отчёты добавлены 14.11 без сборки и проверки на телефоне** — код написан
в облачной сессии Андрея, где Android SDK недоступен. Нужны `py mobile/build.py --offline`
(тесты и Lint) и проход на телефоне.

## Сценарий

1. На стартовой камере автоматически распознаются QR и строки латинской таблички.
   Найденное оборудование подтверждается перед открытием. Доступны ручной ввод
   серийного номера/маркировки, определение по фото со списком кандидатов и ручной поиск.
   Ввод номера раскрывается кнопкой «Ввести номер с таблички», чтобы оставить больше места камере.
   Через 10 секунд ожидания появляется подсказка ручного выбора. Подсказка, ошибки,
   предупреждения и индикатор запроса показываются поверх камеры и не меняют размер превью.
   Подсказка исчезает при обнаружении QR-кода, номера или кандидатов оборудования;
   в AR-осмотре — при обнаружении узла. Если что-то найдено раньше 10 секунд,
   таймер уже не показывает подсказку. При новом входе на экран ожидание начинается заново.
2. Карточка содержит «Обзор», дерево «Состав», «Параметры» со счётчиком отклонений,
   «История». Названия, номера, параметры и рекомендации приходят с бэкенда.
3. «Начать AR-осмотр»: поверх узлов только цветные рамки, без информационных плашек
   и соединительных линий. Распознанные узлы с именем, значком статуса и уверенностью
   доступны списком под камерой. Причина и рекомендуемое действие открываются нажатием на рамку.
4. Панель «Требуют проверки» показывает причины, подсказки, действие и «Не в кадре».
   Типы, не поддерживаемые детектором, доступны через карточки.
5. Нажмите рамку. При неоднозначности выберите узел из предложенных кандидатов;
   для узла вне карточки выводится соответствующее сообщение.
6. «Анализировать» вырезает узел с запасом 15% с каждой стороны из исходного кадра,
   соответствующего выбранной рамке. Во время запроса виден индикатор; после анализа
   открывается карточка узла с результатом.
7. В карточке узла три самостоятельных блока: норматив, расчёт ресурса, визуальный анализ.
   Нехватка данных перечислена явно. Оговорки анализа показаны вместе с результатом.
8. «Зарегистрировать осмотр»: пять типов работ; для дефекта и замечания обязателен
   комментарий. Можно приложить последний визуальный анализ. После записи обновляются
   карточка и история. Замена доступна только для конкретного компонента.

При потере связи показывается ошибка с повтором. Если ответ на сохранение осмотра потерян,
перед повторной записью нужно проверить историю: сервер мог успеть сохранить осмотр.
Кнопка «Повторить» в этом случае перечитывает карточку, а не отправляет запись второй раз.

## Камера и координаты

CameraX `Preview` и `ImageAnalysis` используют общую область видимости. Кадр обрезается
по `cropRect` и поворачивается до отправки. Превью — `FILL_CENTER`: изображение заполняет
всю область камеры без чёрных полос, лишнее обрезается по центру. Преобразование рамок
учитывает эту обрезку. Рамки API — `[x, y, ширина, высота]` в долях кадра.
Кадр для `detect` сжимается в JPEG шириной 640; одновременно отправляется один запрос,
интервал между началами запросов — не менее 700 мс. Живое превью от этого не замедляется.
Анализатор не преобразует в Bitmap кадры чаще раза в 150 мс, чтобы уменьшить лишние выделения памяти.

Рамки сопоставляются по типу, узлу карточки и близости положения, независимо от порядка
в ответе. Мелкое дрожание координат подавляется, умеренные изменения сглаживаются,
переход занимает 420 мс. Метаданные и статусы обновляются из каждого ответа без сглаживания.
При пропуске узла рамка удерживается 900 мс (прикрывает один пропущенный цикл), затем
гаснет за 500 мс; отсутствующая в последнем ответе рамка недоступна для выбора.
При зависшем запросе последнее положение удерживается максимум 3 секунды и затем гаснет.
Настройки времени — `ArTiming` в `DetectionTracker.kt`.

Поверх узлов — только рамки; распознанные узлы доступны списком в нижней
панели. Панель «Требуют проверки» можно развернуть. При выборе узла фиксируется именно
его исходный кадр и исходная рамка: сглаженные координаты используются только для отрисовки,
запоздалый ответ `detect` не меняет снимок для анализа. Экран при работе камеры не гаснет.

Это AR-наложение в плоскости кадра; пространственных якорей и ARCore нет.
Скорость и совпадение рамок с предметом нужно измерить на телефоне с настоящим ИИ.

## Без интернета

- В APK включены `com.google.mlkit:barcode-scanning:17.3.0` и
  `com.google.mlkit:text-recognition:16.0.1`. Варианты с загрузкой моделей не используются.
- Нет удалённых шрифтов, картинок, аналитики приложения и отчётов об ошибках.
  Регистрация отправщика телеметрии Data Transport удалена из манифеста ML Kit;
  автоматический загрузчик шрифтов EmojiCompat отключён.
- HTTP-клиент принимает только числовой локальный IPv4, не использует системный прокси
  и не следует перенаправлениям. Все запросы идут только на сохранённый адрес бэкенда.
- Карточки и история хранятся на ПК в SQLite; при недоступном ПК приложение показывает
  ошибку связи. Отсутствие интернета и отсутствие связи с ПК — разные случаи.
- Офлайн-приёмка закрыта командой 14.11, 13:00 — [статус стенда](../docs/stand.md).
  После замены APK проверить затронутые действия; повторная съёмка кабеля и холодного
  старта не нужна. Проверка состава APK сама по себе не заменяет запуск на телефоне.

Выбор встроенных моделей описан в документации Google:
[QR](https://developers.google.com/ml-kit/vision/barcode-scanning/android),
[текст](https://developers.google.com/ml-kit/vision/text-recognition/v2/android).

## Проверки разработчика

`py mobile/build.py --offline` запускает JUnit, Android Lint и сборку.
Тесты проверяют стабильность рамок при перестановке одинаковых типов, дрожании и пропусках,
устаревание, сохранение исходных координат для анализа, пересчёт координат, запас обрезки у краёв, разбор ответов всех запросов
контракта, поле multipart и путь запроса, допустимые адреса, запрет внешнего перенаправления.
JSON-примеры получены HTTP-запросами к настоящему бэкенду с временной БД и заглушкой ИИ.

Для обновления моделей и примеров при согласованном изменении контракта:

```powershell
py mobile/generate_models.py
backend/.venv/Scripts/python.exe mobile/tests/export_fixtures.py
```

Экспорт примеров запускает отдельный бэкенд на случайном порту localhost и отдельной
временной базе; базу стенда не трогает. Нужны установленные зависимости бэкенда.

Перед приёмкой на телефоне проверьте все четыре способа идентификации и ручной выбор,
отказ разрешения камеры, совпадение рамок в портретном режиме, `ambiguous`/`not_in_card`,
пустой кадр, все пять типов осмотра, историю после перезапуска, потерю связи и полный
сценарий после свежей установки без интернета. Видео, скриншот и отметки «Тел» в матрице
делаются после этой проверки.
