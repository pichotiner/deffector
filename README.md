# Deffector — AR-помощник инженера по осмотру оборудования

Прототип для хакатона «Кибер 102», задача КСТ Энерго Инжиниринг: интеллектуальная система
анализа состояния промышленного оборудования.

Инженер наводит телефон на оборудование. Приложение определяет, что это за оборудование,
загружает его цифровую карточку, находит в кадре узлы, требующие внимания, и подсвечивает
их цветными метками поверх изображения с камеры. По каждому узлу видно:

- что увидел ИИ на снимке;
- сколько осталось ресурса;
- какие параметры вне уставок;
- что делать дальше.

Результат осмотра инженер записывает в историю оборудования.

**Работает без интернета.** Телефон, сервер и ИИ-модели связаны только локальной сетью
предприятия. Снимки и данные оборудования не покидают её периметр.

## Архитектура

```
 ┌──────────────────────┐   HTTP, Wi-Fi   ┌─────────────────────────┐  HTTP, 127.0.0.1  ┌─────────────────────────┐
 │ Android-приложение   │ ──────────────► │ Бэкенд                  │ ────────────────► │ ИИ-сервис               │
 │ камера, QR, текст,   │   кадры, запросы│ FastAPI + SQLite        │  кадр / вырезанный│ детектор узлов,         │
 │ AR-метки, формы      │ ◄────────────── │ карточки, ресурс,       │  узел             │ мультимодальная модель, │
 │                      │  рамки + статусы│ сопоставление, история  │ ◄──────────────── │ идентификация по фото   │
 └──────────────────────┘                 └─────────────────────────┘  рамки, категория └─────────────────────────┘
        телефон                                       сервер в локальной сети предприятия (один ПК с GPU)
```

- Телефон общается **только с бэкендом**. Бэкенд вызывает ИИ-сервис и дополняет его ответ
  данными цифровой карточки: к рамке «манометр» добавляет, какой это узел из карточки,
  его ресурс, параметры, итоговый цвет, причину и рекомендуемое действие.
- Все тексты для экрана бэкенд отдаёт готовыми. Приложение показывает их как есть.
- Обмен телефон ↔ бэкенд — 11 запросов. Описание без интернета — в
  [`backend/openapi.json`](backend/openapi.json), примеры — в разделе 5 [плана](plan/README.md).
  Обмен бэкенд ↔ ИИ — в [`docs/ai-contract.md`](docs/ai-contract.md).
- Ни одна часть не обращается во внешнюю сеть. Бэкенд это подтверждает автотестом:
  весь сценарий проходит при запрете любых соединений, кроме локальных.

## Технологии

| Часть | Технологии |
|---|---|
| Приложение | Kotlin, Jetpack Compose, CameraX; ML Kit — QR и текст, модели встроены в APK; метки — Compose Canvas поверх превью камеры |
| Бэкенд | Python, FastAPI, Pydantic (контракт проверяется на каждом ответе), SQLite |
| ИИ-сервис | Python, FastAPI; детектор с открытым словарём OWLv2 base (`google/owlv2-base-patch16-ensemble`); мультимодальная модель Qwen2.5-VL 7B через Ollama; CLIP ViT-B/32 (LAION-2B) — идентификация по фото. Все модели локальные, на GPU: 7,8 ГБ видеопамяти, рамки — 23 раза в секунду, анализ узла — 1,6 с |
| Стенд | один ПК с Windows и видеокартой, телефон в той же сети Wi-Fi; запуск — `python stand.py` |

Числа скорости и 7,8 ГБ в строке ИИ — замер 13.11 на **ПК Тимофея, RTX 5070**, не
частота кадров телефона и не замер при звонке на ПК Павла. Приёмка 14.11 на том же ПК:
настоящий стенд и полный API-сценарий прошли. Работа без интернета на стенде и телефоне
Павла подтверждена участниками, запись сценария просмотрена; офлайн-приёмка закрыта
Тимофеем 14.11, 13:00. Отдельная съёмка холодного запуска не требуется для сдачи
([матрица покрытия](docs/coverage.md)).

## Установка и запуск

Нужны: ПК с Windows (или Linux) и Python 3.12 (подойдёт 3.13); видеокарта NVIDIA для ИИ-сервиса;
Android-телефон в той же сети Wi-Fi. Интернет — только при первой установке.

```
git clone https://github.com/pichotiner/deffector.git
cd deffector
python stand.py
```

`stand.py` запускает ИИ-сервис, ждёт загрузки моделей, запускает бэкенд и печатает
«СТЕНД ГОТОВ» с адресом для телефона. При первом запуске обе службы сами ставят свои
зависимости.

| Часть | Подробности |
|---|---|
| Стенд целиком, сбой, чек-листы | [`docs/stand.md`](docs/stand.md) |
| Бэкенд | [`backend/README.md`](backend/README.md) — настройки, демо-данные, тесты |
| ИИ-сервис | [`ai/README.md`](ai/README.md) — модели, веса, требования к видеокарте |
| Приложение | [`mobile/README.md`](mobile/README.md) — сборка и установка APK |

Приложение: установить APK по кабелю, в настройках указать адрес из «СТЕНД ГОТОВ»,
затем войти по почте и паролю. Демо-учётные записи:

| Роль | Почта | Пароль | Что может |
|---|---|---|---|
| Инженер | `engineer@kst.local` | `Engineer-102` | карточки, AR-осмотр, ИИ-анализ, запись результатов осмотра |
| Мастер | `master@kst.local` | `Master-102` | всё, что инженер, и выгрузка отчётов |
| Администратор | `admin@kst.local` | `Admin-102` | карточки, выгрузка отчётов, учётные записи; осмотр не проводит |

Права проверяет сервер. Отчёт об осмотре — в PDF и Excel: кнопки на экране оборудования
(мастер и администратор). Основание — [ответы организаторов](docs/tz/organizers-qa.md).

Вход и отчёты собраны в актуальный APK, Windows-проверки — **140 тестов бэкенда**,
**24 JUnit** приложения. Установка/проверка нового APK на телефоне Павла ещё ожидается;
запасное видео снято до добавления входа и отчётов. Хэш APK —
[`mobile/README.md`](mobile/README.md).

Полезные команды:

```
python stand.py --reset                 # сбросить базу к демо-данным и запустить
python backend/check_scenario.py --image demo/reference/PU-001/case_pump_01.jpg   # проверка через бэкенд; записывает осмотры и затем сбрасывает локальную БД
python backend/reset_db.py              # сброс базы
cd backend && python -m pytest          # автотесты бэкенда
```

## Как пройти сценарий

Распечатайте [`demo/print/print.pdf`](demo/print/print.pdf): QR-код, табличку с маркировкой
и серийным номером для каждого образца. Объекты показа — листы
[`demo/photos/show/show.pdf`](demo/photos/show/show.pdf). Подписи пакета — ожидания по
исходным фото, не гарантия распознавания распечаток. Актуальный порядок —
[`docs/presentation/speech.md`](docs/presentation/speech.md): манометр открыть из списка
«Требуют проверки», камера — на Э1 (двигатель), затем лист 6 (арматура с течью),
лист 9 в основной показ не включать. Листы 4, 5 и 8 в показ не брать;
листы 1, 2, 3 и 7 — запасные после проверки с телефоном. Фото листа должно заполнять
экран телефона. Э1 (`PU-001`) и Э3 (`PU-002`) — эталоны для проверки «Определить по фото»;
их снимки телефоном и проверка при свете показа пока не подтверждены.

Красный двигатель после `--reset` — сохранённый демо-осмотр 12.11, не результат новой
камеры и не остаток тестов. Чистый лист 9 не включать в основной показ: на телефоне
Павла подтверждено ложное сообщение о коррозии, причина ещё не установлена. Если анализ
вернёт «видимых проблем не обнаружено», общая метка останется **серой**: норматива
ресурса двигателя нет. Гарантировать такой ответ по этому листу нельзя.

| Шаг ТЗ | Что делает инженер | Что видно |
|---|---|---|
| 1 | Открывает приложение | Экран камеры; при первом запуске и после выхода — вход по почте и паролю |
| 2 | Наводит на QR-код (или табличку с номером, или само оборудование) | «Насосный агрегат Wilo CronoLine-IL 65/160 — подтвердить?»; ручной выбор — список с поиском |
| 3 | Подтверждает | Карточка: модель, характеристики, состав, параметры — вибрация и температура из данных заказчика, давление выше уставки красным; история |
| 4–5 | Открывает осмотр | Список «Требуют проверки» с причинами и подсказка «Наведите камеру на …» |
| 6, 8 | Наводит камеру на агрегат | Цветные рамки на узлах с подписью и причиной; «Анализировать» — признаки на снимке, категория, уверенность |
| 7 | — | Итоговый статус узла: визуальный анализ + ресурс + параметры + записанные дефекты |
| 9 | Нажимает на метку | Карточка узла: характеристики, норматив, расчётный ресурс, визуальный анализ, прошлые проверки, рекомендация |
| 10 | «Проверено», «Дефект», «Замечание», «Обслуживание» или «Замена» | Запись в истории; после обслуживания или замены ресурс пересчитан |

## Демо-данные — из материалов заказчика

Два образца оборудования (ТЗ 4.5), оба — из материалов кейса ([`docs/case/`](docs/case/README.md)):
состав узлов, нормативы и регламенты обслуживания — из документации и паспортов заказчика,
вибрация и температура — из его баз значений с его уставками и диагнозами. Где документация
говорит «по состоянию», норматива нет и в карточке — экран так и пишет.

Журналов эксплуатации в материалах нет, поэтому **учёт эксплуатации — демонстрационные
данные**: наработка, даты установки и замен, история осмотров, давление, арматура и манометр
`PU-001`, показания `PU-002`. Это подписано в карточке каждого образца на экране.

| | `PU-001` | `PU-002` |
|---|---|---|
| Оборудование | насосный агрегат Wilo CronoLine-IL 65/160-5,5/2 (центробежный, 5,5 кВт) | агрегат насосный винтовой AMS PCP60S12/3 01 Ex B1 HNBR DTS, №1 |
| Источник | сводный документ Wilo, базы вибрации и температуры | паспорта агрегата, двигателя, мотор-редуктора, термопреобразователя; инструкция по ЭиО |
| QR / номер | `KST:PU-001` / `SN2024-004587` | `KST:PU-002` / заводской `21031004-1` |
| Узлы | электродвигатель, насос, трубопроводная обвязка | электродвигатель BRA160M4 11 кВт, насос, мотор-редуктор WXRF87 |
| Комплектующие | 2 задвижки, манометр, фланец, торцевое уплотнение MG12, подшипники двигателя, рабочее колесо, муфта | статор и ротор винтовой пары, торцевое уплотнение, термопреобразователь ПТ 0304, реле РТЗ-1М, фланцы |
| Параметры | 9: вибрация (СКЗ, 1x, 2x, ВЧ-шум), температура подшипника и обмоток, обороты — из баз заказчика; давление — выше уставки | 4 — пределы из паспорта |
| История | 9 записей: ТО-1, ТО-2, замена уплотнения после сухого хода… | 4 записи: замена статора, поверка… |

В данных есть каждый случай из ТЗ:

- срок замены наступил — подшипники двигателя (20 600 из 20 000 ч);
- ресурс приближается к порогу — задвижка и уплотнение (89 %), ТО-1 через 5 дней;
- обслуживание просрочено — поверка манометра и термопреобразователя;
- параметр вне уставок — давление на выходе;
- данных недостаточно — фланец без даты установки, рабочее колесо и статор без норматива;
- два однотипных узла — две задвижки;
- замены в истории.

По данным заказчика с 15.11 у агрегата развивается дисбаланс, затем расцентровка и износ
подшипника. Любой момент показывается одной командой:
`DEFFECTOR_TELEMETRY_AT="2026-11-17 02:00" python backend/reset_db.py` — рабочее колесо
становится красным: «Тревога: … — высокий дисбаланс рабочего колеса».

Полный перечень — в [`backend/README.md`](backend/README.md). Распознаются ИИ четыре типа
узлов: электродвигатель, манометр, запорная арматура, фланцевое соединение
([словарь](docs/component-types.md)).

## Ограничения

- Два образца оборудования; параметры — замеры из баз заказчика на выбранный момент,
  а не поток с датчиков в реальном времени. Учёт эксплуатации — демонстрационные данные.
- ИИ распознаёт четыре типа узлов и четыре вида видимых признаков: коррозию, течь или
  подтёки, механические повреждения и следы перегрева (только у электродвигателя).
- ИИ-анализ — предварительный осмотр по изображению. Внутренние неисправности так не
  определяются, а «видимых проблем не обнаружено» не означает исправность — это написано
  на экране при каждом результате.
- Уверенность анализа — оценка самой модели, а не калиброванная вероятность.
- Ошибочная рамка может задать неверный тип и последующему анализу. Опыты проверки типа
  и CLIP-фильтра 14.11 отклонены из-за регрессий, в службе их нет; рабочие модели и пороги
  прежние. Подсчёт числа найденных узлов не равен точности координат рамок
  ([результаты](ai/README.md)).
- Детектор с камеры телефона слабее на крупных планах: мелкий узел находится, только когда
  он заполняет кадр, а на части кадров появляется лишняя рамка двигателя. Решение
  остаётся за инженером: анализ — только по нажатию, на показе — проверенные кадры.
- Метки привязаны к текущему кадру, а не к пространству.
- Расчёт ресурса — ориентировочный: по нормативу и учёту, без условий эксплуатации.
- Нет шифрования трафика: сеть считается доверенной. Вход и роли есть; учётными записями
  управляет администратор запросами к серверу, экрана для этого в приложении нет.
- Приложение только для Android.
- Один сервер с видеокартой; без связи с ним телефон не работает.
