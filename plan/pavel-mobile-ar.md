# План Павла — мобильное приложение и AR

Сначала прочитай [README.md](README.md): там рамки демо, контракт API, статусы и график.
Текст задания — в [ТЗ](../docs/tz/TZ.md); формулировки сверяй с ним.
Твоя зона — папка `mobile/` и всё, что инженер видит на экране. Кроме того, **защита
проходит онлайн и показываешь ты**: бэкенд и ИИ-сервис на защите работают на твоём ПК,
поэтому стенд — тоже твоя зона (раздел «Стенд на твоём ПК» ниже).

## Что должно получиться

Android-приложение, на котором подряд проходят все 10 шагов сценария ТЗ: навёл камеру →
оборудование определено → карточка загружена → видны узлы, требующие проверки →
подсказка, куда навести камеру → анализ узла → цветные метки поверх изображения →
подробная карточка узла → запись о выполненных работах.

Твои пункты ТЗ: 4.1 (экраны), 4.4 (целиком), 4.6 (формы), отображение 4.2, 4.3 и 4.5.

## Технологии

| Задача | Чем делаем |
|---|---|
| Язык и интерфейс | Kotlin, Jetpack Compose, один модуль, `minSdk 26` |
| Камера | CameraX: `Preview` + `ImageAnalysis` |
| QR-код | ML Kit Barcode Scanning, вариант со **встроенной в APK** моделью |
| Текст маркировки и серийного номера | ML Kit Text Recognition (латиница), вариант со **встроенной в APK** моделью |
| Сеть | Retrofit + OkHttp + kotlinx.serialization |
| Метки поверх камеры | Compose `Canvas` поверх превью |

Адрес сервера задаётся на экране настроек и сохраняется. Это адрес твоего ПК в домашней
сети. Для него разреши в манифесте незашифрованный трафик по HTTP.

**Приложение не должно требовать интернета** (ограничение организаторов, раздел 4.1 README):

- у ML Kit есть два варианта каждой библиотеки: один подгружает модель из интернета при
  первом запуске, другой несёт её внутри APK. Нужен второй — проверь по документации,
  какую зависимость подключаешь;
- шрифты, значки и картинки — только внутри приложения, ничего не грузится по ссылкам;
- никакой аналитики, отчётов о сбоях и других библиотек, которые обращаются в сеть;
- единственный сетевой адрес, к которому обращается приложение, — сервер из настроек.

## Экраны

1. **Камера — идентификация** (стартовый).
2. **Ручной выбор оборудования** — список с поиском.
3. **Оборудование** — вкладки: «Обзор», «Состав», «Параметры», «История».
4. **AR-осмотр** — камера с метками и панелью «Требуют проверки».
5. **Карточка узла**.
6. **Регистрация осмотра** — форма.
7. **Настройки** — адрес сервера, имя инженера, проверка связи.

### Этап 1. Каркас и идентификация — до 20:00, 13.11

- [ ] Сетевой клиент: модели данных строго по контракту, обработка ошибок и отсутствия связи

- [ ] **QR-код (4.1):** камера непрерывно ищет QR → `lookup?qr=` → карточка подтверждения

- [ ] **Маркировка и серийный номер (4.1):** в том же потоке кадров распознаётся текст;

- [ ] **По изображению (4.1):** кнопка «Определить по фото» → `POST /api/identify/image` →

- [ ] **Экран оборудования, вкладки «Обзор» и «Состав» (4.1, 4.5):** идентификатор, модель,

- [ ] **Тексты не собирай сам** (README, раздел 6.1, п. 5): причины, подсказки, сообщения

- [ ] **13.11, до 22:00 — объекты показа** (п. 6), вместе с Тимофеем: выбрать и распечатать
      фото узлов; дальше всё проверять на них.

### Этап 2. Основной функционал — до 12:00, 14.11

- [ ] **Вкладка «Параметры» (4.1):** название, текущее значение, единица, уставки, время
      замера. Отклонение выделено красным со значком и текстом из `message`. Если есть
      отклонения — предупреждение на вкладке «Обзор» и счётчик на заголовке вкладки.
- [ ] **AR-осмотр, поток кадров (4.4):** кадр уменьшается до 640 пикселей по ширине,
      сжимается в JPEG и уходит в `detect`. Одновременно в пути только один запрос;
      следующий кадр отправляется после ответа.
- [ ] **AR-метки (4.4):** для каждой рамки из ответа рисуются:
  - рамка цветом `attention_level`;
  - значок статуса (чтобы статус читался не только по цвету);
  - подпись: название узла и процент уверенности распознавания;
  - краткая причина предупреждения (`reason`) и рекомендуемое действие (`recommended_action`).
- [ ] **Пересчёт координат:** рамки приходят в долях кадра — пересчитай в координаты
      превью с учётом поворота и обрезки изображения. Проверь на телефоне в портретной ориентации.
- [ ] **Плавность:** между ответами сервера рамка плавно перемещается к новому положению;
      рамка, пропавшая из ответов, гаснет через полсекунды.
- [ ] **Нажатие на метку (4.4):** открывает карточку узла. Для `match: ambiguous` — сначала
      выбор из кандидатов. Для `not_in_card` — сообщение «узел не найден в карточке оборудования».
- [ ] **Панель «Требуют проверки» (шаги 4–5):** список из `attention`; у каждого узла
      причины и подсказка `hint` — «Наведите камеру на …». Узлы, которых нет в кадре
      (`not_in_frame`), помечены «не в кадре».
- [ ] **Анализ узла (шаг 6):** кнопка «Анализировать» на выбранной метке → вырезать область
      рамки с запасом 15 % из кадра полного разрешения → `analyze` → показать результат.
      Пока идёт анализ — индикатор; анализ длится несколько секунд.
- [ ] **Карточка узла (шаг 9, 4.3, 4.5):** сверху название, тип, характеристики. Ниже
      **три отдельных блока с заголовками**:
  1. «Нормативный срок службы» — срок в годах / часах / циклах, интервал обслуживания,
     даты установки, последней замены и последнего обслуживания.
  2. «Расчётная оценка остаточного ресурса» — процент выработки, остаток, ожидаемая дата,
     на чём основана оценка (`basis`). При `insufficient_data` — крупная надпись
     «Недостаточно данных для оценки» и перечень недостающего (`missing_data`).
  3. «Результат визуального анализа» — категория дословно из ТЗ, найденные признаки,
     объяснение, рекомендация, уверенность, время анализа, текст-оговорка (`disclaimer`).
     При `no_visible_issues` дополнительно: «Отсутствие видимых дефектов не подтверждает
     исправность оборудования».

  Ещё ниже: связанные параметры, рекомендуемые действия, предыдущие результаты проверок
  и кнопка «Зарегистрировать осмотр».
- [ ] **Регистрация осмотра (4.6):** выбор типа — «Компонент проверен», «Обнаружен дефект»,
      «Замечание», «Обслуживание», «Замена»; поле комментария (обязательно для дефекта
      и замечания); переключатель «приложить результат визуального анализа»; имя инженера
      из настроек. После сохранения — обновить карточку узла и историю.
- [ ] **Вкладка «История» (4.5):** записи от новых к старым: дата, тип, узел, комментарий,
      кто выполнил, рекомендация.

## Чек-лист приёмки (формулировки ТЗ)

**4.1**
- [ ] Оборудование определяется по QR-коду.
- [ ] Оборудование определяется по маркировке.
- [ ] Оборудование определяется по серийному номеру.
- [ ] Оборудование определяется по изображению.
- [ ] Цифровая карточка загружается из базы данных.
- [ ] Отображаются модель и состав оборудования.
- [ ] Отображаются технические параметры, отклонения сигнализируются.
- [ ] Ручной выбор доступен при ошибке и при невозможности распознавания.

**4.2 и 4.3 (отображение)**
- [ ] Категории показаны дословно: «видимых проблем не обнаружено», «рекомендуется проверка»,
      «обнаружены признаки возможного дефекта».
- [ ] Видны объяснение причины, рекомендация и уверенность модели.
- [ ] Нормативный срок, расчётная оценка и результат визуального анализа — три разных блока.
- [ ] Нехватка данных показана явно.
- [ ] Результаты расчёта ресурса и визуального анализа показаны вместе.
- [ ] «Видимых проблем не обнаружено» нигде не подано как «исправно».

**4.4**
- [ ] Информационные метки отображаются поверх изображения с камеры.
- [ ] Узлы, требующие проверки, выделены.
- [ ] Статусы обозначены цветом, значком и рамкой.
- [ ] В метке — краткая причина предупреждения и рекомендуемое действие.
- [ ] Компонент можно выбрать и открыть его подробную карточку.

**4.5 (отображение)**
- [ ] Видны идентификатор, модель, характеристики, перечень узлов, нормативные сроки,
      даты установки и замены, история осмотров, предыдущие результаты и рекомендации.

**Без интернета**
- [ ] Свежеустановленное приложение проходит весь сценарий при выключенной передаче данных,
      в сети без выхода в интернет.

**4.6**
- [ ] Можно подтвердить, что компонент проверен.
- [ ] Можно зафиксировать дефект или замечание.
- [ ] Можно зарегистрировать обслуживание или замену.
- [ ] Результат сохраняется в истории и виден после перезапуска приложения.

## Если времени не хватает

Порядок, в котором нельзя жертвовать: QR и ручной выбор → карточка → AR-метки → карточка
узла → регистрация осмотра → анализ узла → маркировка и серийный номер → идентификация
по изображению. Каждый пункт всё равно должен быть сделан до сдачи; порядок только
определяет, что доводить до блеска в последнюю очередь.
