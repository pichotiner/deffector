# План Андрея — бэкенд, данные, цифровой двойник, презентация

Сначала прочитай [README.md](README.md): там рамки демо, контракт API, статусы и график.

Твоя зона — папки `backend/`, `docs/`, QR-коды и таблички в `demo/`, а также сведение
трёх частей в одно целое и защита.

## Что должно получиться

1. Бэкенд с базой, в которой лежат цифровые карточки двух образцов оборудования.
2. Все запросы контракта из раздела 5 README.
3. Расчёт эксплуатационного ресурса.
4. Сведение результата ИИ с данными карточки.
5. Запись и хранение осмотров.
6. Развёрнутое демо, презентация и документация.

Твои пункты ТЗ: 4.3 и 4.5 целиком, серверная часть 4.1 и 4.6, сопоставление из 4.2, раздел 5.

## Технологии

| Задача | Чем делаем |
|---|---|
| Сервис | Python, FastAPI — описание API создаётся автоматически. Встроенная страница проверки запросов подгружает свои скрипты из интернета и на стенде без сети не откроется — на показе на неё не рассчитываем |
| База | SQLite, один файл; наполняется скриптом `seed` |
| Тесты | pytest — на расчёт ресурса и сопоставление |
| Запуск | одна команда поднимает бэкенд; адрес ИИ-сервиса — в настройках |

### Этап 2. Ресурс, сведение, осмотры — до 12:00, 14.11

- [x] **Расчёт ресурса (4.3).** Для оборудования в целом и для каждого компонента:

  1. Точка отсчёта — дата последней замены, а если замен не было — дата установки.
     Наработка и циклы считаются от той же точки.
  2. По каждому показателю, для которого есть и норматив, и фактические данные,
     считается доля выработки:
     - календарная: прошедшее время ÷ нормативный срок в годах;
     - по наработке: часы ÷ нормативные часы;
     - по циклам: циклы ÷ нормативные циклы.
  3. Итоговая выработка — **наибольшая** из долей (осторожная оценка).
  4. Остаток — по каждому показателю отдельно; ожидаемая дата исчерпания — по показателю,
     который закончится первым, исходя из средней скорости расхода с точки отсчёта.
  5. Обслуживание: следующая дата = дата последнего обслуживания + интервал.
  6. Статус:
     - `due` — выработка 100 % и больше **или** дата обслуживания наступила;
     - `approaching` — выработка 80 % и больше **или** до обслуживания 30 дней и меньше;
     - `ok` — иначе;
     - `insufficient_data` — нет ни одного показателя с нормативом и фактическими данными.
  7. `basis` — на чём основана оценка, словами: «Оценка по календарному сроку от даты
     последней замены; наработка не предоставлена».
  8. `missing_data` — каких данных не хватает. Заполняется и при частичной нехватке:
     оценка есть, но видно, что она неполная.
  9. `message` — одна фраза для экрана: «Срок обслуживания наступил 11 дней назад».

  Пороги 80 % и 30 дней — в настройках, не в коде.
