# Проверка координат, 14.11

`labels.json` — 16 исходников без копирования фотографий, пути от корня репозитория.
Все четыре класса, общие виды и крупные планы; листы 1, 4, 5, 8, 9 и Э1 включены.
Это **не снимки телефона**. Разметка сделана визуально агентом, не независимым экспертом;
границы некоторых узлов спорны. До изменения детектора набор должен проверить Тимофей.

## Правила разметки

- `objects` — видимая прямоугольная область узла, `[x, y, ширина, высота]` в долях кадра.
  У частично обрезанного фланца размечается видимая часть плиты, не отдельные гайки.
  Рамки арматуры не должны включать целиком соседние трубы и другие задвижки.
  Корпус двигателя с установленным верхним блоком в `sheet09` размечен целиком;
  одна рамка только на синем корпусе может не достичь IoU 0,5. Это ограничение определения
  границ, а не свидетельство отсутствия распознавания двигателя.
- Стыковочная полумуфта на листе 1 — **не трубный фланец**. Резьбовые гайки у крана — тоже.
- `evaluated_classes` — классы, размеченные **полностью в пределах видимого кадра**,
  кроме явно указанных исключений. Только для них неразмеченный участок считается фоном.
  Например, в насосной оцениваются только двигатели; остальные классы не получают FP
  за неразмеченные задние планы. Неразмеченный класс не даёт ни TP, ни FP, ни FN.
- `ignore_regions` — явно исключённые обрезанные/размытые объекты **конкретного класса**.
  Сначала сопоставляются эталоны; лишь затем несопоставленная рамка исключается, если
  не менее половины **её площади** попало в такую область. Это не TP.
- В клеммной коробке нельзя разметить границу целого двигателя: `electric_motor` исключён
  из оценки этого кадра, а не объявлен отсутствующим.
- `group` связывает варианты одного исходника; группа не может попадать одновременно
  в `tune` и `control`. Манометр с коррозией и двигатель с коррозией — `tune`, остальные
  исходники — `control`. Изменения детектора на этих данных не подбирались.
- Анализ дефектов остаётся в прежнем `demo/photos/labels.json`. Входы сравнения типа
  отдельно замораживает `ai/tools/quality_check.py`: предполагаемый тип, группа,
  соответствие типу (`true` / `false` / `null` — нужен просмотр), режим входа и SHA-256.
  Тип исходного фото не доказывает тип вырезанной области: в частности, гайка с листа 5
  не является достаточным изображением фланцевого соединения.

## Измерение

```powershell
ai\.venv\Scripts\python ai/tools/evaluate_boxes.py --report runs/boxes.json --draw runs/boxes
```

Предсказания обходятся по убыванию уверенности, при равенстве — в исходном порядке.
Каждое сопоставляется с ещё свободным эталоном **того же класса** с максимальным IoU
не ниже 0,5; при равенстве выбирается меньший индекс эталона. Повторная рамка — FP.
Есть TP, FP, FN, precision и recall по классам, отдельно по `tune` / `control`.
Нулевой знаменатель — `null` («нет данных»), а не 100 %.

Оценить сохранённые ответы без моделей:

```powershell
ai\.venv\Scripts\python ai/tools/evaluate_boxes.py --predictions runs/boxes.json --report runs/boxes_replay.json
```

Также читаются JSON от `evaluate.py` (пути относительно `demo/photos`, меняется
`--prediction-root`) и `show_check.py` (пути в поле `file`). Если для кадра нет ответа,
инструмент останавливается, а не считает это пустой детекцией.

В отчёте сохранены рамки, решения по каждой рамке, пропуски, параметры и SHA-256 разметки.
На картинке зелёные GT, жёлтые TP, розовые остальные предсказания, серые исключения.
Тесты искусственных примеров — `ai/tests/test_evaluate_boxes.py`.

**Старый подсчёт количества не равен этой оценке.** На листе 1 он засчитал два фланца,
хотя одна рамка на полумуфте; на листе 5 — один фланец, хотя рамка на гайке.
Даже правильный тип с чрезмерно широкой рамкой может не пройти IoU 0,5: в отчёте это
одновременно FP предсказания и FN эталона. Поэтому результаты нельзя представлять
как долю кадров, в которых модель вообще заметила узел.
